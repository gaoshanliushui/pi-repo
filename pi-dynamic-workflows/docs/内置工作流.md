# 内置工作流

扩展注册了 5 个斜杠命令，每一个都生成一段确定性的脚本交给 `runWorkflow` 执行。脚本生成器与命令注册分别在 `src/builtin-commands.ts` 与 `src/{deep-research,code-review,adversarial-review}.ts`。

## 1. `/deep-research <question>`

文件：`src/deep-research.ts → generateDeepResearchWorkflow()`。

四阶段流水线：Queries → Gather → Verify → Report。

```
phase('Queries')
plan = agent('为这个问题设计 ${angles} 个不同的搜索 query', schema: { queries: string[] })
queries = plan.queries.slice(0, angles)

phase('Gather')
gathered = parallel(queries.map(q => () => agent('用 web_search + web_fetch 抓资料；只回报页面里实际说的内容', schema: { sources: [...] })))
allSources = gathered.flatMap(g => g.sources)

phase('Verify')
verdict = agent('把同一个事实的多个来源分组；保留被 ${minSupport} 个不同 URL 支持的；丢弃弱单源', schema: { supported, discarded })

phase('Report')
report = agent('用 supported claims 写一份带 URL 引用的研究回答')

return { question, queries, supported, report }
```

调 `runWorkflow(..., { tools: [...createCodingTools(cwd), ...createWebTools()] })` 注入 web 工具。每个 gather agent 走 `web_search` → `web_fetch` 两条链路。

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `args.question` | 必填 | 待研究问题 |
| `args.angles` | `4` | 搜索角度数 |
| `args.minSupport` | `2` | 一个 claim 至少被多少个独立来源支持才保留 |

`createWebTools()` 提供 `web_search` / `web_fetch`（`src/web-tools.ts`）。

最终结果用 `pi.sendMessage({ customType: 'deep-research', content, display: true })` 回投，`content` 优先取 `result.report`，否则 JSON dump。

## 2. `/adversarial-review <task>`

文件：`src/adversarial-review.ts → generateAdversarialReviewWorkflow()`。

三阶段：Investigate → Refute → Consensus。

```
phase('Investigate')
findings = agent('调查任务并列出具体可验证的发现', schema: { findings: string[] })

phase('Refute')
judged = parallel(findings.map(f => () =>
  parallel(reviewers 个 agent('你是怀疑论审稿人；尝试 REFUTE 这个发现；不确定时默认 real=false', schema: { real, reason }))
))
survivors = judged.filter(j => j.realVotes / j.totalVotes >= threshold)

phase('Consensus')
report = agent('基于幸存的发现写最终报告；注明被丢弃的数量')
```

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `args.task` | 必填 | 待审任务 |
| `args.reviewers` | `2` | 每个 finding 多少个 reviewer |
| `args.threshold` | `0.5` | 至少多少比例 reviewer 标 real 才算幸存 |

特点：每个 finding 都由 N 个"假设要反驳"的人独立投票，幸存下来的才能进最终报告。

## 3. `/multi-perspective "<topic>" [angle …]`

文件：`src/adversarial-review.ts → generateMultiPerspectiveWorkflow(topic, perspectives)`。

两阶段：Perspective Analysis → Synthesis。

- topic 必填，**带引号**。
- 至少 2 个 angle；否则默认 `[technical, product, security, user experience, maintainability]`。
- 每个 angle 一个 agent 并行跑"从该角度分析 topic"，最后由一个 synthesis agent 合并。

返回 `{ analyses, synthesis }`；回投时优先取 `result.synthesis`，否则 JSON dump。

## 4. `/code-review [target]`

文件：`src/code-review.ts → generateCodeReviewWorkflow()`。`MAX_DIFF_CHARS = 200_000`。

三阶段：Find → Verify → Report。

7 个 finder agent 并行：

| 角度 | tier | 关注点 |
| --- | --- | --- |
| A | `medium` | 逐行正确性扫描：反转条件、off-by-one、null 解引用、错误变量、吞掉的错误 |
| B | `medium` | 删除行为审计：被删代码原本强制的契约是否在新位置重新保证 |
| C | `medium` | 跨文件调用追踪：函数签名/行为变了之后调用点还正确吗 |
| D | `small` | 复用：新增代码是否复制了已有 helper / pattern |
| E | `small` | 简化：可推导的冗余状态、可共享的 copy-paste、引入的死代码 |
| F | `small` | 效率：冗余 I/O、可并行的串行、启动/热路径上的阻塞 |
| G | `big` | 抽象层级：是不是"在错误的层修问题"（UI 补偿数据模型问题、绕路补丁而非根因） |

Verify 阶段对每个候选 finding 跑一个 verifier agent，产出 3 选 1 的 verdict：

- `CONFIRMED`：能追踪到 diff 里的具体失败。
- `PLAUSIBLE`：关注点有效但不确定。
- `REFUTED`：错了或已经处理过。

过滤掉 `REFUTED`，再按 A/B/C > D/E/F > G 的优先级排序，取 top 10 给 synthesis agent 写 markdown 报告。

### 4.1 diff 来源

`<target>` 决定 diff 从哪儿来（由 `builtin-commands.ts` 解析）：

| 输入 | 解析为 |
| --- | --- |
| （空） | `git diff HEAD` |
| 纯数字（`42`） | `gh pr diff 42` |
| 含 `..`（`HEAD~3..HEAD`） | `git diff <range>` |
| 其他 | `git diff HEAD -- <target>` |

`execFile` 调用 + 64MB buffer（覆盖任何 `gh pr diff` 输出，Node 默认 1MB 会爆）。

`MAX_DIFF_CHARS` 之外会截断并向用户 warning："截断到前 N 字符，未覆盖的部分请缩小范围"。

## 5. `/codebase-audit <scope> "<check1>" ["<check2>" …]`

文件：`src/deep-research.ts → generateCodebaseAuditWorkflow(scope, checks)`。

三阶段：Individual Checks → Cross-Validation → Report。

- 必填 scope（项目内路径，截断 60 字符）。
- 至少 1 个 check。
- 每个 check 一个 agent 并行跑，标签取 `check.toLowerCase().replace(/[^a-z0-9]+/g, '-').slice(0, 20)`。
- cross-validation agent 把所有发现合并去伪，report agent 写带优先级的报告。

返回 `{ findings, validated, report }`。

## 6. 通用行为

- 全部走 `runWorkflow(generatedScript, { cwd, args, tools, onPhase })`。
- `onPhase` 把 `ctx.ui.setStatus(cmd, '${cmd}: ${phase}')` 同步到状态栏。
- 错误被 catch → `ctx.ui.notify` 报错，状态栏清空。
- 完成后调 `pi.sendMessage({ customType: '<cmd>', content: reportText(result), display: true })`，`reportText` 优先取 `result.report`（或 `/multi-perspective` 的 `result.synthesis`），否则 JSON.stringify。

## 7. 注册流程

`extensions/workflow.ts` 在扩展装载时调：

```ts
registerBuiltinWorkflows(pi, { cwd })
```

`registerBuiltinWorkflows` 内部对每个命令做 `if (!alreadyRegistered(pi, name)) pi.registerCommand(name, ...)`，所以其它扩展抢先注册同名的命令时不会冲突。

## 8. 与通用 `workflow` 工具的关系

- 通用 `workflow` 工具：模型在运行时按需生成脚本，需要 `agent() / parallel() / ...` 的灵活组合。
- 内置 `/...` 命令：用户在前台显式触发，脚本是确定性的、字符串模板生成的，无须模型参与决策。

二者最终都走 `runWorkflow` —— 内置命令本质上是"预生成的脚本 + 预打包的提示"。
