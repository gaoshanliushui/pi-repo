# 工作流运行时与执行流程

本文深入 `src/workflow.ts`，讲清一段用户脚本是怎么被解析、在沙箱里执行、产生子代理调用、并最终产出结果的。重点是 `runWorkflow` 的内部状态机。

## 1. 入口：`runWorkflow(script, options)`

签名：

```ts
function runWorkflow<T>(script: string, options?: WorkflowRunOptions): Promise<WorkflowRunResult<T>>
```

`options` 里有这些关键字段：

| 字段 | 作用 |
| --- | --- |
| `cwd` | 解析项目级 agent 定义、工作树等的基目录 |
| `args` | 透传给脚本的全局 `args` |
| `concurrency` | 并发上限（默认 `min(16, hardwareConcurrency - 2)`） |
| `agentRetries` | 可恢复失败的重试次数（0–3） |
| `tokenBudget` | 整次 run 的 token 上限；到达后 `agent()` 抛 `TOKEN_BUDGET_EXHAUSTED` |
| `maxAgents` | 整次 run 的子代理上限（默认 1000） |
| `agentTimeoutMs` | 单个子代理超时（默认 `null`，不强制） |
| `resumeJournal` | resume 时传入的 `Map<callIndex, JournalEntry>` |
| `signal` | 外部 AbortSignal（Esc / 工具调用取消） |
| `confirm` | `checkpoint()` 的交互答复函数 |
| `loadSavedWorkflow` | `workflow('name', args)` 查表函数 |
| `sharedRuntime` | 嵌套子 run 共享的 `SharedRuntime` |
| `sharedStore` | 跨 run 共享的 `SharedStore` |
| `modelRegistry` | 主 Pi 会话传入的 model registry |
| `mainModel` | 主会话的 `provider/id`，回退模型 |
| `persistAgentSessions` | 是否把子代理 transcript 落盘为 Pi 会话 |
| 各类 `onXxx` 回调 | `onLog / onPhase / onAgentStart / onAgentEnd / onAgentJournal / onTokenUsage` |

`runWorkflow` 内部做的事情按顺序：

1. 调用 `parseWorkflowScript(script)` 拿到 `meta` 和去掉 meta 导出后的 `body`。
2. 解析 `meta.phases[].model` + `meta.model` 为 `routingConfig`。
3. 决定 `runId`（`run-${Date.now().toString(36)}`）、`maxAgents`、`agentTimeoutMs` 等默认值。
4. `loadAgentRegistry(cwd)` 一次性快照，避免中途 `.md` 改动影响本次 run。
5. 构造 `WorkflowLogger`。
6. 初始化 `RuntimeState`（logs、phases、callSeq=0、firstMiss=+∞、phaseBudgets）。
7. 选 `WorkflowAgent`（注入或新建）。
8. 构造/沿用 `SharedRuntime`（限流器、agentCount、spent、tokenUsage、depth=0）。
9. 构造/沿用 `SharedStore`。
10. 在闭包内定义 `log/phase/budget/throwIfAborted` 以及 `agent/parallel/pipeline/workflow/verify/judgePanel/loopUntilDry/completenessCheck/retry/gate/checkpoint`。
11. 构造 `vm.createContext({ ...globals })`。
12. 把 `DETERMINISM_PRELUDE + async IIFE(body)` 装入 vm 沙箱运行。
13. `try` 块里：等待结果，emit `onTokenUsage`，返回 `WorkflowRunResult`。
14. `finally` 块里：自己创建的 `SharedStore` 调 `dispose()`。

## 2. 脚本解析：`parseWorkflowScript`

要求脚本的第一条语句必须是 `export const meta = { ... }`。这一步用 `acorn` 解析 AST，但**只解析第一行**，目的有三：

- 拿到 `name` / `description`（必填，校验）、`phases`（可选）、`model`（可选）作为路由默认值。
- 把 meta 块从脚本中切掉，得到纯函数体 `body`。
- 校验"是否声明了 meta"——不写 meta 直接抛 `SCRIPT_VALIDATION_ERROR`。

`evaluateLiteral` 只接受 AST 中的字面节点（`ObjectExpression` / `ArrayExpression` / `Literal` / `TemplateLiteral`（不带插值）/ `-NumberLiteral`），不允许 spread、计算键、`__proto__/constructor/prototype` 等保护性键。这样做是为了在解析阶段就拒绝掉 `export const meta = someFunction()` 这种"运行时报错"的写法。

`validateMeta` 进一步要求 `name` / `description` 是非空字符串、`phases` 是 `{ title: string }[]`、`model` 若存在必须是字符串。

## 3. 沙箱与确定性

`vm.createContext` 接受的是一个新对象，里面放：

- 注入的全局：`agent / parallel / pipeline / workflow / verify / judgePanel / loopUntilDry / completenessCheck / retry / gate / checkpoint / log / phase / args / cwd / process / budget / console`。
- **不**注入宿主 `Date / Math / Object / Array / JSON / Promise / Set / Map` 等等——这些是 vm realm 自带的，每次新建 realm 时复制一份。

然后在脚本前面拼接 `DETERMINISM_PRELUDE`，把 realm 内的 `Math.random` / `Date.now` / `new Date()` 全部改成抛错。它通过 `vm` 自己的 `Math` / `Date` / `Reflect` 闭包完成，不引入宿主 `Function`，所以不是宿主逃逸。注释里明确写了："这是 best-effort 防意外，不是安全边界"。

> 任何会引入"每次运行都不同"的代码都会被拦截——这就是为什么 resume 能放心用账本回放。

## 4. `agent()` 生命周期

```ts
agent(prompt, options) →
  1. 抛 if aborted
  2. 检查 shared.agentCount < maxAgents（agentCount++ 在限流前同步完成，避免并发绕过）
  3. 检查 token 预算（>=0 才允许新 agent）
  4. 检查相位子预算
  5. resolveAgentType(agentType) → agentDef
  6. 决定 explicitModel = opts.model ?? agentDef.model
     决定 modelSpec = explicitModel ?? opts.tier ? undefined : phaseModel
  7. 决定 displayModel = modelSpec ?? mainModel
  8. 计算 callIndex = callSeq++
  9. 计算 callHash = sha256(prompt, model, tier, phase, agentType, agentDefKey, schema)
 10. 计算 deltaKey = `${runId}:${callIndex}`  ← 这就是 SharedStore 用 run-unique 键的原因
 11. 同步 shared.agentCount++
 12. 查 resumeJournal：
     - 命中且 hash 一致且 callIndex < firstMiss：直接返回 cached.result，并 applyDelta。
     - 否则把 firstMiss 推到 min(firstMiss, callIndex)，开始 live run。
 13. limiter(() => real work)
```

限流器内做的是真正的工作：

1. 决定 `timeout` 与 `retryAttempts = normalizeAgentRetries(opts.retries ?? agentRetries)`。
2. emit `onAgentStart`。
3. 若 `opts.isolation === "worktree"`（或 `agentDef.isolation === "worktree"`）：`createWorktree(cwd, '${runId}-${callIndex}-${label}')`。
4. 进入 `try`：
   - 最多 `maxAttempts = retryAttempts + 1` 次。
   - `withTimeout(agentRunner.run(...), timeout, label)`。
   - `throwIfProviderLimit(messages)`：检测 SDK 的 assistant 错误消息，命中 `usage limit / quota / 429 / ...` 时抛 `PROVIDER_USAGE_LIMIT`（`recoverable: false`）。
   - 命中 `schema` 时走 `resolveStructuredOutput`：re-prompt、prose 提取、再失败抛 `SCHEMA_NONCOMPLIANCE`。
   - 没 schema 但空文本：抛 `AGENT_EMPTY_OUTPUT`（`recoverable: true`）。
   - 成功时 `recordTokens(result)`：从子代理 `onUsage` 拿真实使用量，累计到 `shared.tokenUsage` 和 `shared.spent`。
   - `onAgentJournal({ index, hash, result, storeDelta: store.commitDelta(deltaKey) })` —— **关键**：账本里记的不是整张 store 快照，而是这个 agent 写过的 key→value 增量，resume 时按 callSeq 顺序累加，解决"并行 agent 谁后写谁赢"的乱序问题。
   - `onAgentEnd(...)`。
5. `catch`：包成 `WorkflowError`，根据 `recoverable + attempt < maxAttempts` 决定重试；用尽后 emit `onAgentEnd` 标记为 `error`，可恢复则返回 `null`，不可恢复则抛出。
6. `finally`：若 worktree 存在则 `removeWorktree(worktree)`，无论成功/超时/异常都清掉。

### 4.1 模型解析优先级

`agent.ts` 的 `resolveAgentModelSpec` 给出 "model 怎么落地" 的另一段链路（与上面 6 步互补）：

```
opts.model  >  resolveTierModel(opts.tier, tiersConfig)  >  resolveTierModel("medium", tiersConfig)  >  mainModel
```

- `opts.model` 是绝对 `provider/modelId[:thinking]`，最高优先级。
- 否则若指定 `tier`，查 `~/.pi/workflows/model-tiers.json`；命中就用，未命中回退 `mainModel`。
- 否则如果用户配置过 tiers，就用 medium tier；目的是"用户既然配了 tiers，就让它们生效"。
- 都没有：用 `mainModel`（主会话的模型）。

注意 `WorkflowAgent` 用 `modelRegistry` 解析 `modelSpec` 为 SDK 认识的 `Model<any>` 对象 + `thinkingLevel`，然后通过 `createAgentSession({ model, thinkingLevel, ... })` 落定。

## 5. `parallel()` / `pipeline()`

```ts
parallel(thunks)  // thunks 必须是 () => Promise 形态，而不是已经创建的 Promise
pipeline(items, ...stages)  // 每个 stage 接收 (prev, original, index)
```

两者都内部用 `Promise.all` 跑，但都做了：

- `throwIfAborted` 检查。
- 严格 `typeof thunk !== "function"` 的入参校验——故意拒绝"传 promise"，因为 `parallel(items.map(item => agent(...)))` 是常见错误，这种写法是 0 并行。
- `try/catch` 每个 thunk：可恢复错误吞掉返回 `null`，不可恢复错误（`TOKEN_BUDGET_EXHAUSTED` / `AGENT_LIMIT_EXCEEDED`）抛出终止整个 run。
- `pipeline` 还会在每个 stage 之间也抛 `throwIfAborted`。

## 6. 嵌套 `workflow(nameOrScript, args)`

`workflowFn` 复用外层 `runWorkflow`，但通过 `options.sharedRuntime` / `options.sharedStore` 把限流器、token 账、SharedStore 透传给子 run。`shared.depth >= 1` 时抛错——只允许一层嵌套。

子 run 的 `runId` 写成 `${parentRunId}-nested${shared.depth}`，配合 `${runId}:${callIndex}` 的 `deltaKey`，避免父子 run 同 index 撞 store key。

`resumeJournal` 显式传 `undefined`：嵌套 run 应当独立跑，不复用父的账本。

## 7. 内置质量模式

`verify` / `judgePanel` / `loopUntilDry` / `completenessCheck` / `retry` / `gate` 全部建立在 `agent()` 与 `parallel()` 之上，所以它们都是普通 `agent()` 调用——稳定的 callSeq、稳定的 callHash 全部自动继承，意味着 resume 同样适用。

| 名字 | 模式 |
| --- | --- |
| `verify(item, { reviewers, threshold, lens })` | 让 N 个"反对者"独立判断一个声明是否为真，N ≥ 1，threshold 默认 0.5，可选 `lens` 字符串数组分配不同视角 |
| `judgePanel(attempts, { judges, rubric })` | N 个 attempts 每个交给 judges 个 judge 打分，按平均分+输入顺序选最优 |
| `loopUntilDry({ round, key, consecutiveEmpty, maxRounds })` | 不断调用 `round()` 直到连续 K 轮没新东西（按 `key` 去重）；遇 token/agent 上限就 break |
| `completenessCheck(args, results)` | 让一个 agent 列出"还缺什么"，做收尾 critic |
| `retry(thunk, { attempts, until })` | 至多 N 次跑 thunk，until 满足即停 |
| `gate(thunk, validator, { attempts })` | 跑 thunk → 交给 validator 给 ok/feedback → 不 ok 就把 feedback 喂回去再试 |

## 8. `checkpoint()` —— 人类决策点

签名：

```ts
checkpoint(promptText, { default?, headless: 'default' | 'abort', kind?, choices?, timeoutMs? })
```

机制：

- 也走 callSeq + callHash，因此 resume 同样生效。
- 如果 `options.confirm` 存在，调它拿人类答复。
- 否则根据 `headless` 决定：默认走 `default ?? true`；`headless: 'abort'` 时抛 `WORKFLOW_ABORTED`。
- 关键：headless 模式绝不"挂起"——后台 run 永远会继续。

## 9. `phase()` 与子预算

`phase(title, { budget })`：

- 切换 `state.currentPhase`，把 title 加进 `state.phases`。
- 若提供 `budget` > 0，从当前 `shared.spent` 起算一个相位子预算。
- 软门禁：`agent()` 每次检查"该 phase 已用 `phaseSpent >= budget`"则抛 `TOKEN_BUDGET_EXHAUSTED`；`>= 0.8 * budget` 时记一次警告。
- 软（spent 在 agent 完成后才累计），不是硬限制。
- 脚本里 try/catch 相位就能让后续 phase 继续跑。

## 10. `budget`

```ts
const budget = {
  total: opts.tokenBudget ?? null,
  spent: () => shared.spent,
  remaining: () => opts.tokenBudget == null ? Infinity : Math.max(0, opts.tokenBudget - shared.spent),
}
```

`Object.freeze`，避免脚本意外改写。`spent()` / `remaining()` 是函数调用，每次拿最新值。

## 11. 退出与清理

- `runWorkflow` 正常结束时：emit `onTokenUsage(shared.tokenUsage)`，把日志 persist 到 `<runsDir>/<runId>.log`，返回 `WorkflowRunResult`。
- `finally` 块里：如果 `options.sharedStore` 未传入（自己创建），`store.dispose()` 清空内存；嵌套 run 继承父 store，不能自己 dispose。
- 抛错时由调用方（`executeRun`）统一处理，把 `WORKFLOW_ABORTED` / `PROVIDER_USAGE_LIMIT` 等分类成 `paused` / `failed` / `aborted`，见 [background-management.md](./background-management.md)。

## 12. 执行流示例

`scan → review → verify` 三相位的脚本对应到运行时的状态机：

```
parseWorkflowScript
  meta = { name, description, phases: [Scan, Review, Verify] }
  state.currentPhase = "Scan"

vm.runInContext
  ① phase('Scan')    → state.currentPhase = "Scan",   onPhase 事件
  ② await agent(...)  → callSeq 0, hash 0, limiter 内真实运行
                      → onAgentStart / onAgentJournal / onAgentEnd
  ③ phase('Review')   → state.currentPhase = "Review", onPhase 事件
  ④ await parallel(items.map(i => () => agent(...)))
                      → 一次性预约 callSeq 1..N（并行）；limiter 内部串行化 16 个
  ⑤ phase('Verify')   → state.currentPhase = "Verify", onPhase 事件
  ⑥ await agent(...)  → callSeq N+1（以脚本中位置算）, hash N+1
  ⑦ return { ... }    → 脚本顶层返回，vm.runInContext resolve

finally:  store.dispose(), emit onTokenUsage
```

下一次 `/workflows resume <id>` 走的是同一段代码，只是多了：

- `callIndex < firstMiss` 的 agent() 命中账本（replay cached.result + applyDelta）；
- `firstMiss` 之后全部走 live run，可能出现 `parallel()` 的 fan-out 又重新预约新的 callSeq。
