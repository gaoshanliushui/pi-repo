# 后台运行管理

本文讲清"一次 run 是怎么从工具调用变成可暂停/可恢复的长期任务"的，覆盖 `WorkflowManager`、`RunPersistence`、文件锁和事件流。

## 1. `WorkflowManager` 总览

`src/workflow-manager.ts` 是一个 `EventEmitter`，把 `runWorkflow` 包成可被外部控制的状态机。核心数据结构：

```ts
class ManagedRun {
  runId: string;
  status: "running" | "paused" | "completed" | "failed" | "aborted";
  snapshot: WorkflowSnapshot;          // 实时状态（TUI/任务面板读这个）
  result?: WorkflowRunResult;
  error?: WorkflowError;
  controller: AbortController;          // 整个 run 的中止信号
  startedAt: Date;
  script: string;                       // 留作 resume
  args?: unknown;
  journal: JournalEntry[];              // 累积账本
  lease?: RunLease;                     // 跨进程文件锁
  background: boolean;                  // 后台还是前台同步
}
```

它暴露给外界的几个能力：

| API | 用途 |
| --- | --- |
| `startInBackground(script, args, exec)` | 启动后台 run，立刻返回 `{ runId, promise }` |
| `runSync(script, args, exec)` | 同步阻塞执行，但仍注册到 manager 中（让 TUI/任务面板能看见），返回 `WorkflowRunResult` |
| `pause(runId)` | 调 `controller.abort()`，status 置 `paused`，释放 lease，emit `paused` |
| `stop(runId)` | 类似 `pause`，但 status 置 `aborted`（彻底放弃，resume 拒绝） |
| `resume(runId)` | 从持久化读脚本+账本，重新跑未完成部分 |
| `getRun(runId)` / `getSnapshot(runId)` | 给 TUI 用 |
| `listRuns()` | 当前 session 的所有 run（按 `setSessionId` 过滤） |
| `listAllRuns()` | 不带 session 过滤的全量 |
| `deleteRun(runId)` | 删除 run 状态 |
| `setSessionId` / `setMainModel` / `setModelRegistry` | 在 `session_start` 时由扩展注入 |
| `getPersistence()` | 给 save workflow 命令用 |

事件名（`EventEmitter`）：

- `log`：新日志条目 → 任务面板、TUI 刷新。
- `phase`：进入新 phase → TUI 把对应 phase 高亮。
- `agentStart` / `agentEnd` / `agentHistory` / `tokenUsage`：单个 agent 生命周期。
- `resumed`：resume 成功。
- `paused` / `stopped` / `complete` / `error`：run 终止。

## 2. 启动：startInBackground

```
parseWorkflowScript  → 取 meta
生成 slug (meta.name → kebab-case，截 40 字符) + runId = `${slug}-${generateRunId()}`
acquireRunLease(runId)   ← 跨进程文件锁
构造 ManagedRun { status: "running", controller, background: true, lease }
this.runs.set(runId, managed)
persistence.save({ ...initial state... })   ← 立刻落盘
executeRun(managed, script, args, exec)  →  fire-and-forget
return { runId, promise }
```

`generateRunId()` 形如 `${Date.now().toString(36)}-${random 6 字符}`，是 base36 时间戳加随机后缀。

`exec` 字段（`ExecOptions`）允许调用方传：

- `resumeJournal`：resume 时携带账本
- `maxAgents / agentTimeoutMs / externalSignal / onProgress / tokenBudget / concurrency / agentRetries / confirm`

## 3. 同步：runSync

签名与 `startInBackground` 类似，但 `background: false`：

```
createManaged()  // 生成 runId + snapshot
acquireRunLease(managed.runId)
this.runs.set(managed.runId, managed)
persistRun(managed)   ← 立刻让 TUI/任务面板能 list 到
return executeRun(managed, script, args, exec)
```

`workflow` 工具的 `background: false` 路径走 `runSync`，所以"前台同步"也仍然在 manager 中可见、有 TUI 订阅。

## 4. `executeRun`：把 runWorkflow 包成可观测任务

`executeRun(managed, script, args, exec)` 是把 `runWorkflow` 与"事件 + 持久化"缝起来的核心：

1. 解构 `exec`，合并 `defaultAgentTimeoutMs / defaultAgentRetries / concurrency` 默认值。
2. `externalSignal` 注册到 `managed.controller`：若外部信号已 aborted，立刻 abort；否则一次性监听。
3. 调用 `runWorkflow(script, { cwd, args, agent, mainModel, modelRegistry, persistAgentSessions, signal: managed.controller.signal, ... })`，并把所有 `onXxx` 桥接到：
   - 改 `managed.snapshot`（追加/更新 agent、调 `recomputeWorkflowSnapshot`）。
   - `this.emit("...", event)`。
   - `onProgress?.(snapshot)` 回调。
   - 每收到一个 `onAgentJournal` 就 `managed.journal = dedupe-by-index, push; persistRun(managed)`。
4. 成功：status → `completed`，写最终 `result`，emit `complete`，`persistRun(managed)`，释放 lease。
5. 失败：分类
   - `signal.aborted` → `aborted`（保留已有的 `paused`/`running` 等中间状态）
   - `PROVIDER_USAGE_LIMIT`（quota 用尽）→ `paused`（`pauseReason: "usage_limit"` + `resetHint`），emit `paused`
   - 其他 → `failed`，emit `error`
   - 写盘 + 释放 lease
   - 抛出

## 5. 暂停 vs 停止 vs 恢复

| 操作 | 入口 | 行为 | 是否可恢复 |
| --- | --- | --- | --- |
| `pause(runId)` | `/workflows pause <id>` 或工具调用 | `controller.abort()` + status=`paused` + emit `paused` | ✅ |
| `stop(runId)` | `/workflows stop <id>` 或 TUI `x` | `controller.abort()` + status=`aborted` + emit `stopped` | ❌ |
| `resume(runId)` | `/workflows resume <id>` 或 TUI `r` | 重新读持久化脚本+账本 → `executeRun({ resumeJournal })` | 仅在 paused/failed 状态可用 |

`pause` 调 `controller.abort()`：这会让所有正在进行的子代理（它们都通过 `signal.addEventListener("abort", onAbort)` 注册了）一并被取消，正在 await 的子代理抛出"Subagent was aborted"，被 `wrapError` 包装为 `WORKFLOW_ABORTED`（`recoverable: true`）。但因为是"主动 abort"且 `signal.aborted` 为 true，所以 `executeRun` 走 `aborted` 分支。

`resume(runId)` 行为：

```
拒绝: status 已是 running / aborted
接受: persistence.load(runId) 拿脚本 + journal
   acquireRunLease(runId)
   new ManagedRun { status: "running", controller, script, args, journal: persisted.journal, lease, background: true }
   runs.set(runId, managed)
   persistRun(managed)   ← 立刻把"resumed"状态落盘
   emit resumed
   executeRun(managed, persisted.script, persisted.args, { resumeJournal: Map(persisted.journal.map(...)) })
```

`runWorkflow` 接到 `resumeJournal` 后，按 callSeq + callHash 做"未变动前缀"回放：命中的 agent() 直接返回缓存结果（不计 token、计入 store delta）；未命中的从该 callIndex 开始全部 live run。

## 6. 持久化：`RunPersistence`

`createRunPersistence(cwd)` 返回的对象提供 4 个方法 + 2 个锁方法：

| 方法 | 说明 |
| --- | --- |
| `save(state)` | 写 `runsDir/<runId>.json`（tmp → rename 原子写）+ `runsDir/<runId>.json.bak` 兜底 |
| `load(runId)` | 先查 primary，再 primary.bak，再 legacyDir，JSON.parse 失败回退 .bak |
| `list()` | 遍历 `runsDir` 与 `legacyRunsDir`，按 `updatedAt` 倒序，按 runId 去重 |
| `delete(runId)` | 删 primary/legacy + .bak + .tmp + .lock |
| `acquireRunLease(runId)` | 写 `<runId>.lock`（带 `pid/token/startedAt`），失败时检查现有锁进程的 pid 是否还活着，若活着返回 null |
| `releaseRunLease(lease)` | 校验 token 匹配后 unlink |
| `getRunsDir()` | 暴露路径 |

### 6.1 跨进程文件锁

```json
{
  "runId": "auth_audit-lpx7",
  "runPath": "/home/me/.pi/workflows/projects/auth_audit-ab12cd34ef56/runs/auth_audit-lpx7.json",
  "pid": 48211,
  "startedAt": "2026-07-14T10:11:12.000Z",
  "token": "48211-lpx7z8b-x4c9"
}
```

`acquireRunLease` 用 `wx` flag（O_EXCL）原子创建：

- 成功 → 拿到锁。
- EEXIST → 读现有锁的 `pid`，用 `process.kill(pid, 0)` 探测存活；存活返回 null（锁被他人持有），死亡则删旧锁重试。
- 重试 2 次都失败返回 null。

旧版或异常退出留下的锁会自动被 GC：探测 `pidIsAlive` 返回 false 就把锁删掉。

### 6.2 启动时的孤儿恢复

`new WorkflowManager(...)` 调 `recoverStaleRuns()`：

```
for each persistedRun in listAllRuns():
  if status === "running" and not in this.runs:
    acquireRunLease  // 抢到锁说明别人已经死了
    persistence.save({ ...p, status: "paused" })
    releaseRunLease
```

把"正在跑但实际已经死了"的 run 标为 `paused`，让用户能 resume，绝不标 failed（避免丢失账本）。

### 6.3 原子写

```ts
writeFileSync(`${path}.tmp`, json)
renameSync(`${path}.tmp`, path)   // 同一文件系统上原子
writeFileSync(`${path}.bak`, json)   // 兜底
```

`rename` 在同分区是原子操作；`.bak` 是上一份成功写盘的快照——若 primary 损坏，load 会按 primary → primary.bak → legacy primary → legacy primary.bak 顺序尝试。

## 7. 任务面板 / TUI 是怎么订阅的

`extensions/workflow.ts` 在 `session_start` 调 `installTaskPanel(pi, manager, ctx.ui, ...)`，把 `agentStart / agentEnd / log / phase / tokenUsage` 全部桥接到 ctx.ui 的 widget。

`/workflows` 命令的 TUI（`openWorkflowNavigator`）走 `manager.listRuns()` 拿快照，再用 `manager.getRun(id)` 看实时状态变化。

## 8. 一次 run 的完整生命周期

下面把"用户发起 → 完成/中断 → 可能恢复"画成一个时间线：

```
t0  用户输入触发 "workflow"
t1  workflow 工具被调用 → startInBackground(script)
    - acquireRunLease (创建 .lock)
    - persistRun (status=running)
    - executeRun (fire-and-forget, 内部)
t2  executeRun → runWorkflow (vm sandbox)
    - 解析 + 注入 globals
    - 第一个 agent() 调起
    - 状态：manager 收到 agentStart → emit → 面板/TUI 刷新
    - 每次 agent 完成：onAgentJournal + onAgentEnd → 写盘 (runs/<id>.json 覆盖更新)
t3  用户按 Esc / 关掉 Pi
    - executeRun 的 catch 进入 WORKFLOW_ABORTED 分支
    - status → "aborted" 或 "paused"（如果是 quota 触发的）
    - persistRun 落盘
    - releaseRunLease
    - (如果没爆走 releaseRunLease 路径，跨进程锁依然存在)
t4  Pi 重启 → new WorkflowManager → recoverStaleRuns
    - 探测所有 "running" 的 persistedRun
    - 若没人持锁则标为 "paused"
t5  用户 /workflows resume <id>
    - 读脚本+账本
    - 构造新 ManagedRun { journal, resumeJournal, lease }
    - executeRun
    - runWorkflow 拿到 resumeJournal → callIndex < firstMiss 的 agent() 全部走缓存
    - firstMiss 之后的 agent() 全部重新跑
t6  最终一次 persistRun 落盘 → 释放 lease → run 关闭
```

## 9. 配置项的来源

`executeRun` 里 `defaultAgentTimeoutMs / concurrency / agentRetries` 优先取自 `exec`（工具或命令显式传入），其次 `WorkflowManager` 的构造选项（由 `loadWorkflowSettings({ cwd })` 注入的 `~/.pi/workflows/settings.json` 提供）。

也就是说：

- 工具调用 `params.concurrency: 4` → 这一次 run 限制 4 并发。
- 用户在 settings.json 写 `"defaultConcurrency": 4` → 所有 run 默认 4。
- 都未指定 → `min(16, hardwareConcurrency - 2)`。
